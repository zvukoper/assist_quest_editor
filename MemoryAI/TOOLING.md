# Инструментарий и диагностические приёмы

Этот файл фиксирует инструменты, которые реально используются для разработки и диагностики Assist Quest Editor, и ограничения среды.

## Локальная Linux-среда агента

| Инструмент | Состояние | Функционал |
|---|---|---|
| Git | есть | клонирование, история, diff, ветки, локальные проверки состояния репозитория |
| GitHub | доступен через подключённый GitHub-инструментарий | чтение/изменение файлов, история коммитов, Actions jobs/logs/artifacts, работа с ветками и PR |
| Node.js 22 | есть | JavaScript tooling, CI-скрипты, запуск smoke harness |
| npm / npx | есть | установка Playwright и npm-зависимостей, запуск CLI |
| Chromium | есть | браузерный runtime для Playwright |
| Playwright CLI | есть, 1.57.0 | E2E/smoke/UI диагностика реального DOM/JavaScript |
| Python | есть | анализ данных, быстрые вспомогательные проверки и генерация диагностических инструментов |
| ripgrep (`rg`) | есть | быстрый поиск символов, строк, TODO, ссылок и потенциальных регрессий по дереву исходников |
| curl / jq | есть | HTTP/API диагностика и обработка JSON |
| GCC / make | есть | вспомогательные native-задачи; не являются основным build tool проекта |
| .NET SDK | нет в Linux-контейнере | полноценную .NET сборку не считать локально подтверждённой; проверять через Windows/CI |
| PowerShell | нет в Linux-контейнере | `compile.ps1` физически проверять на Windows/CI |

## Основные практики

### GitHub Actions

CI для проекта является эталонной проверкой Windows-сборки:

В workflow используется push по ветке main, поэтому каждый отдельный commit в main запускает полный набор проверок. Для этой причины действует пакетная схема: связанные изменения накапливаются и отправляются одним commit, а не серией микрокоммитов.

Дополнительная защита workflow — concurrency с cancel-in-progress: true: если новый запуск для main появился до завершения предыдущего, устаревший незавершённый запуск отменяется. Это не заменяет пакетирование, а служит страховкой от случайных повторных запусков.

Рекомендуемый цикл диагностики:
1. накопить целостный набор изменений;
2. локально проверить всё доступное;
3. одним commit отправить пакет в main;
4. дождаться одного полного CI;
5. при ошибке исправить найденную причину и сделать один следующий исправляющий commit.

Не создавать отдельные CI-проходы ради промежуточных перестановок файлов, мелких правок MemoryAI или временных технических изменений, относящихся к той же задаче.
- Node.js / Playwright / Chromium;
- web JavaScript syntax;
- .NET restore/build/test;
- single-file `compile.ps1`;
- диагностический отчёт и TRX artifacts.

При ошибке не считать следующий успешный шаг доказательством полной исправности: смотреть итоговый `final_gate` и диагностический artifact.

### Playwright

Использовать не только для внешнего клика по UI, но и как диагностический harness:
- подгружать именно реальный `editor.js` / `simulator.js`;
- слушать `pageerror`;
- проверять `console.error` / `console.warn`;
- проверять реальные WebView message contracts через test seam;
- фиксировать конкретные DOM/JS значения до и после действия.

Для поведения, которое невозможно гарантированно оценить без реального визуального окна, Playwright считать дополнительным доказательством, а не заменой физической проверки.

### ripgrep

Перед исправлением ошибки:
- искать определение символа;
- искать все вызовы;
- искать старые имена/старые версии;
- проверять, не существует ли второй реализации того же контракта.

Особенно полезен для JS-функций, WebView actions, NodeType, Data Channel keys и VersionInfo.

### curl / jq

Применять для:
- GitHub/HTTP API диагностики;
- проверки JSON fixture;
- сравнения фактического ответа с ожидаемым transport contract.

Не использовать их как замену подключённому GitHub-инструментарию, когда задача требует изменения содержимого GitHub-репозитория.

## WebView2 / `file:` блокировка

Корпоративная политика, security software или браузерный policy layer иногда блокируют `file:` URL. Это не обязательно означает, что сам JavaScript/WebView runtime неисправен.

Диагностический workaround:

1. В тестовом harness создать минимальный HTML как строку.
2. Загрузить его через `data:text/html,...` либо эквивалентный data URL.
3. Внутри документа подключить/встроить тот же реальный JavaScript-код или его фактический тестируемый фрагмент.
4. Проверить поведение реального browser engine: DOM, events, pointer/wheel handling, message bridge seam, ошибки JavaScript.
5. После этого отдельно проверить `file:` путь, когда политика позволяет.

Важно: `data:` workaround используется только для диагностики поведения движка и frontend-логики. Он не доказывает корректность production-загрузки `file:` ресурсов, путей публикации или WebView2 content extraction. Эти части проверяются отдельным тестом.

### Почему это полезно

Если `file:` запрещён, можно отделить две независимые гипотезы:
- проблема в JS/browser behavior;
- проблема именно в способе загрузки локального документа.

`data:` позволяет продолжить диагностику первой гипотезы без изменения production architecture.

## Диагностический лог

Приложение пишет `MemoryAI/LOGS/assist_quest_editor.log`.

В лог должны попадать:
- версия и пути запуска;
- загрузка СДО и число точек;
- WebView2 lifecycle;
- Web UI errors/warnings/unhandled rejections;
- WebView actions;
- Simulator snapshots;
- Runtime transitions/events;
- CI automated test report;
- семь сценариев: Graph / Parameters / Simple Runtime / Interaction / Event / Choice / Save/Load.

Нельзя писать секреты, токены, пароли или иные чувствительные данные.

## Ограничения доверия

Локальное отсутствие .NET/PowerShell означает:
- `node --check` и Playwright можно проверять локально;
- C# compilation и `compile.ps1` нельзя объявлять подтверждёнными только по статическому анализу;
- окончательное утверждение о Windows build — только после успешного Windows CI или фактического Windows build пользователя.

## Правило восстановления контекста

При продолжении работы:
1. проверить `main` и последний commit;
2. прочитать `MemoryAI/INSTRUCTIONS.md`, `MemoryAI/ARCHITECTURE.md`, `MemoryAI/CURRENT_TASK.md`, `MemoryAI/PROJECT_MEMORY.md` и этот файл;
3. проверить последние Actions/логи;
4. перед архитектурными изменениями свериться с `MemoryAI/WOLVENKIT_REFERENCE.md`;
5. не возвращать canonical state в JavaScript и не подключать реальные ETS2/telemetry adapters раньше утверждённого этапа.
