# Инструкции разработки

## 1. Ветки

Работа только в main.

Запрещено создавать feature, dev, fix, experiment и другие рабочие ветки.

Изменения коммитятся непосредственно в main.

## 2. Источник архитектурной истины

Основная архитектура проекта хранится в MemoryAI/ARCHITECTURE.md.

Полная задумка и контекст — в MemoryAI/PROJECT_MEMORY.md.

Текущая задача — в MemoryAI/CURRENT_TASK.md.

При смене агента эти файлы и `MemoryAI/TOOLING.md` обязательны к прочтению до изменения кода. `TOOLING.md` фиксирует доступные инструменты, ограничения среды и диагностический workaround для блокировки `file:`.

## 3. Версии

Формат версии наследуется от ETS2 Assist:

A.B.C.D-ОПИСАНИЕ-RN

Текущая база: 1.0.40.100-QUEST-EDITOR-SANDBOX-R0.

Перед каждым физическим тестированием приложения пользователем необходимо увеличить версию.

Версия должна присутствовать в основных диагностических местах приложения.

## 4. Язык

Все пользовательские интерфейсы — русский язык.

Все пользовательские сообщения — русский язык.

Документация и комментарии — русский язык.

Технические идентификаторы кода, ключи протоколов и имена библиотек могут оставаться на стандартном техническом английском, если это необходимо для совместимости.

Локализация закладывается заранее. Пользовательские строки не должны быть захардкожены внутри бизнес-логики.

## 5. Архитектура

Не смешивать:

- Domain;
- Quest Runtime;
- Data Channels;
- Simulator;
- Web UI;
- WinForms host;
- Game adapters.

Quest Domain не должен ссылаться на ETS2, DayZ, WinForms или WebView2.

Simulator реализует тот же Data Channel contract, который позже будет использовать реальная игра.

## 6. Никаких runtime patch

Запрещены обходы, monkey patching, reflection-подмена состояния и пост-запусковые изменения опубликованных файлов как способ исправить архитектурный дефект.

Правильный путь:

изменить исходный код → собрать → проверить → опубликовать.

Javascript, CSS и web assets также исправляются только в исходниках репозитория.

## 7. Тесты до коммита

Перед каждым коммитом обязательно использовать доступные локальные проверки:

- dotnet build;
- dotnet test;
- Node syntax checks;
- Chromium;
- Playwright;
- web UI smoke tests;
- другие локальные валидаторы, относящиеся к изменённой области.

Если локальный инструмент недоступен, это должно быть явно зафиксировано в диагностике, а соответствующая проверка должна пройти в CI. Полный перечень доступных инструментов и их назначение хранится в `MemoryAI/TOOLING.md`.

## 8. CI

Изменения для одной функциональной задачи накапливать до связного проверяемого состояния, а затем отправлять одним коммитом в main.

Целевой цикл:

изменения → доступные локальные проверки → один коммит в main → анализ результата.

Основной барьер перед сборкой — локальный прогон `ci/run_local.ps1`. Он повторяет тот же набор проверок, что и GitHub CI, и вызывается автоматически из `pull.ps1` перед `compile.ps1`. Если проверки не прошли, сборка не выполняется, а отчёт пишется в `MemoryAI/LOGS/CI_errors.md`.

Автозапуск GitHub Actions по push отключён: `ci.yml` запускается только вручную через `workflow_dispatch`. Причина — экономия времени Windows runner; набор проверок локально тот же.

GitHub CI остаётся обязательным, когда нужна проверка того, что локально получить нельзя:

- чистая среда `windows-latest` без локальных кешей и untracked-файлов;
- зафиксированный в workflow Node.js 22, а не версия с текущей машины.

В этих случаях запускать `ci.yml` вручную и дожидаться результата. Не считать работу завершённой до успешного ручного прогона, если он был необходим.

Не создавать серию промежуточных коммитов только ради отдельных файлов, небольших фиксов или синхронизации MemoryAI, если они относятся к той же задаче.

Цель правила — не создавать множество запусков, которые конкурируют за время Windows runner и затрудняют диагностику.

## 9. Работа с логами

В репозитории существует MemoryAI/LOGS/.

При успешной сборке содержимое MemoryAI/LOGS/ очищается, кроме README.md.

В приложении должна быть кнопка сбора диагностических логов.

Она должна копировать в MemoryAI/LOGS/ все журналы, необходимые агенту для полноценной отладки текущего состояния приложения.

Не копировать бессмысленный мусор.

Успешные commit/push диагностических LOGS не записывать в `MemoryAI/LOGS`: успешный результат должен оставаться только визуальным статусом интерфейса. В лог записывать только неудачные попытки commit/push и соответствующие детали ошибки.

## 10. Уровни логирования

Пока проект не объявлен чистовиком:

app_workflow — подробная последовательность выполнения функций и переходов состояния.

app_data — потенциально шумные значения, снимки каналов и диагностические данные.

Не писать поток текущих координат, частоту таймера и другие данные в app_workflow, если они не являются событием перехода состояния.

## 11. Отсутствие файловых архивов

Пользователю не выдавать файлы проекта для скачивания ради передачи изменений.

Изменения вносить непосредственно в GitHub-репозиторий.

Архивы проекта не использовать как основной способ обмена исходниками.

## 12. UI

Основная оболочка:

C# WinForms.

Визуально сложные части:

WebView2 + HTML/CSS/JavaScript.

Преимущество web UI — удобная вёрстка, быстрый просмотр и Playwright automation.

Web UI не хранит авторитетное состояние.

## 13. Simulator

Simulator обязан использовать реальные Data Channel interfaces.

Нельзя делать отдельную логику «как будто это игра».

Изменение позиции, переменных, инвентаря и событий должно проходить через те же каналы, что и будущие реальные игровые данные.

## 14. Serialization

Canonical model является основной моделью.

JSON — переносимый формат хранения/тестирования.

Нельзя строить runtime непосредственно вокруг структуры конкретного JSON-файла, если это ухудшает расширяемость модели.

Любое изменение схемы сопровождается schema version и migration strategy.

## 15. Расширение

Новая нода добавляется через registry и отдельный handler.

Новый Condition operator не должен требовать переписывания существующих условий.

Новый игровой источник добавляется адаптером.

Новый exporter не должен менять canonical quest model.

## 16. Диагностика ошибок

Ошибки должны содержать:

- подсистему;
- этап;
- идентификатор сущности, если он известен;
- безопасное описание причины.

Не скрывать архитектурные ошибки повторными retry без ограничений.

## 17. Git и пакетирование изменений

Коммиты должны быть тематическими, но связанные изменения одной задачи следует собирать в один законченный пакет.

Не дробить одну исправляемую проблему на цепочку микрокоммитов, каждый из которых запускает полный CI.

Перед отправкой в main сначала накопить согласованный набор изменений, провести все доступные локальные проверки и только затем создать коммит.

Сообщения коммитов — на русском языке.

Не коммитить:

- bin/;
- obj/;
- node_modules/;
- WebView2 cache;
- пользовательские save files;
- временные логи;
- локальные секреты;
- архивы;
- сгенерированные runtime-файлы.

## 18. Тестовая дисциплина

Для новой функциональности сначала писать/обновлять domain tests.

Для web UI — Playwright smoke/regression.

Для интеграции Simulator → Runtime — integration tests.

Физическое тестирование пользователем проводится только после успешного локального прогона проверок и bump версии.

## 19. Обязательная сверка с WolvenKit

Для архитектурных и логических решений Assist Quest Editor обязательным внешним reference является upstream-репозиторий WolvenKit:

https://github.com/WolvenKit/WolvenKit

Перед изменением canonical model, Quest/Scene Graph, Node/Socket/Connection, Runtime, Persistence, Editor infrastructure, adapters/exporters или крупного editor workflow агент обязан:

1. прочитать `MemoryAI/WOLVENKIT_REFERENCE.md`;
2. проверить актуальный `main` WolvenKit;
3. изучить относящиеся к решению source/docs;
4. сравнить предлагаемое решение с их архитектурными принципами;
5. зафиксировать в MemoryAI причину, если наше решение сознательно отличается.

WolvenKit не является абсолютной спецификацией нашего проекта. Мы заимствуем его философию и полезные архитектурные паттерны, но не переносим REDengine/Cyberpunk-specific model один-в-один.

Игнорировать эту сверку при архитектурном изменении запрещено: цель правила — не допускать решений, которые сейчас удобны, но позже ограничат функциональность и потребуют перелома canonical model.


## 20. Workaround для блокировки file:

Если корпоративная политика/защитное ПО блокирует загрузку WebView2 через `file:`, сначала отделять проблему загрузки ресурса от проблемы самого browser engine.

Для этого разрешено использовать тестовый `data:text/html,...` документ и тот же реальный JavaScript, который проверяется в production. Это позволяет диагностировать DOM/events/pointer/wheel/message behavior реального движка без `file:`.

`data:` workaround является диагностическим тестом, а не заменой production architecture. Корректность `file:`-загрузки, publish content и WebView2 extraction должна проверяться отдельно.

Полная процедура закреплена в `MemoryAI/TOOLING.md`.
